Today

Every software request in the company lands on one desk.

It waits

Every operational request needs IT sign-off. They queue.

It's unusable when opened

No justification, no security answer, no cost, no legal position.

The approver becomes the researcher

Two to three hours of vendor research, per tool, by hand.

Nobody did anything wrong. The requester didn't know what to include. The approver wasn't slow — they were buried.

Elapsed time is an estimate and is marked as one throughout. The missing-justification case is real: it happened to an ISO approval last month.

The first idea

Most requests shouldn't reach a person at all.

Before anything else, GreenLight asks one question: do we already own this?

Nobody

We own it and a licence is spare. Access in seconds, logged. No approver.

Finance

We own it, no spare seat. A purchase, not a security question — so it never reaches IT.

IT

New to us, or the last answer has expired. This is the one worth attention.

A catalog hit is not approval. An entry re-escalates when its review date passes, when it drifts out of a legal entity's scope, or when new exploited vulnerabilities appear after the approval. A catalog that never expires is just an allowlist.

What Claude does

The question no database can answer.

Machines answer this

Is anyone attacking it right now? How many critical CVEs? What's the privacy grade?

CISA KEV NIST NVD ToSDR OSV.dev

Four sources, about one second.

Only Claude answers this

Does this vendor hold a current SOC 2? Is there a DPA? Where does our data actually go? Does SSO exist on the tier we're buying?

There is no API for any of it. It lives as prose on trust centres and legal pages, in a different shape for every vendor.

Claude reads those pages and returns typed facts with a source URL for each one — and states plainly what it could not find.

The rule that makes it trustworthy

Every fact carries where it came from.

1verified  from a structured source anyone can re-query
2sourced  found on an identifiable page, URL kept
3claimed  the vendor says so about itself, nothing confirms it
4not found  could not be established

A vendor's word is not evidence

A claimed fact cannot satisfy a blocking requirement — however it arrived.

Not found is a finding

A requirement that can't be evaluated returns more information required. Never a guess.

This is the failure mode that sinks AI tools: confident synthesis of things nobody verified. GreenLight is built so it structurally cannot happen.

software-approval@1.3

More information required

Policy is a versioned file, one per entity. Change a rule, no code changes and nothing is deployed — and every decision is stamped with the version that governed it.

Adding a whole new approval domain is also just a file. Software approvals and ISO document approvals already run through the same engine.

The part I'd show a security lead

Approvals expire. On their own.

→Slack was approved in November with a ten-month review interval.
→That interval ran out today.
→So slack.exe dropped off the endpoint allow list by itself — no ticket, no restart, nobody notified.

And Microsoft 365 is being watched

Six new actively-exploited vulnerabilities have been published since it was approved. It stops self-serving until someone looks again.

The same validity rule governs both the approval queue and what endpoints are permitted to run, so policy and enforcement cannot disagree.

Why the queue shrinks

Every decision made today is one that is never made again.

Approve something new and it joins the catalog. The next person who asks for it gets it in seconds, and the approver never sees the request.

A person still decides — GreenLight never approves anything. What it removes is the research, the chasing, and every request that should never have been asked twice.
